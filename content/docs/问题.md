# Redis



### 一. 共享session使用jwt还是hash

**2026 年企业级主流：两者的“合体变种” —— JWT + Redis**

单纯用 Redis Hash 吧，高并发下 Redis 压力大；单纯用 JWT 吧，安全不可控。于是现在大厂最流行的架构是 **“黑白名单机制”（JWT 负责轻量传输，Redis 负责安全风控）**。

### 现在的标准企业流水线：

1. **生成**：用户登录成功，生成一个 JWT，同时在 JWT 里塞一个随机的 `uuid`（代表本次登录令牌）。
2. **存入 Redis**：把这个 `uuid` 存入 Redis，设置一个过期时间（比如 30 分钟）。**注意：这时候在 Redis 里往往不需要复杂的 Hash 结构了，直接存一个简单的 String 类型的黑/白名单标志即可**（如 `SET jwt:auth:uuid123 1`）。
3. **校验流程**：
   - 请求进来，微服务网关（如 Gateway）首先在本地解密 JWT（**阻断 90% 的无效/非法请求，不占用 Redis 压力**）。
   - 解密成功后，网关再去 Redis 里看一眼：这个 `uuid` 在不在黑名单里（或者在不在白名单里）。
4. **主动踢人**：如果想让用户强行下线，直接去 Redis 里把这个 `uuid` 抹掉或加黑。网关下次一查 Redis 发现被拉黑了，直接拦截。

### 总结（面试回答）

**“Redis 共享 session 现在是用 hash 还是 jwt？”**



> “这两者属于不同的架构演进。传统的 **Redis 共享 Session**，在 Redis 内部使用的是 **Hash 结构** 来存储用户多维度的状态，优点是控制力强。
>
> 但现在微服务架构下，大家更倾向于使用 **JWT** 来实现服务间的**无状态鉴权**。为了解决 JWT 无法主动失效的致命缺点，我们企业里通常会引入 **Redis 作为配合，用 String 结构建立黑/白名单机制**。这样既利用了 JWT 减轻服务内存压力的优势，又保留了随时能将异常用户‘踢下线’的控制能力。”
